ResourceAware

A Lean 4 framework for verified algorithm analysis. Write the algorithm once. Interpret it under independently varying semantic and cost models — and prove the models do not disturb each other.

The idea

An algorithm is a free program over an abstract operation signature: it fixes control flow and the operations it requests, and nothing else. Execution semantics and resource measurement are supplied separately, as two independent structures, and one generic interpreter runs every algorithm.

free program→ semantics→ measured trace→ operation profile→ exact cost→ IsBigO bound

Because a cost model is a separate value, changing it is a theorem-backed no-op on behaviour: mapEvents_runFrom_eq proves that swapping the cost model preserves the returned value, the final state, and the erased operation trace. And because runs produce ordered traces rather than a single accumulated number, one execution answers many cost questions — erase the measurements, keep the operation profile, and reweight it under any charge function.

One algorithm, two cost models

From the executable examples — MergeSort interpreted twice, same trace, different measurements:

def comparisonRun := interpret (CostModel.comparisonOnly) (mergeSort [4, 1, 3, 2])
def kleinbergRun  := interpret (CostModel.kleinberg 1 listStructuralBackend) (mergeSort [4, 1, 3, 2])

#guard comparisonRun.ret.1 == [1, 2, 3, 4]   -- same sorted result
#guard exactCost comparisonRun == 5          -- five key comparisons
#guard exactCost kleinbergRun  == 13         -- split 4 + merge 4 + comparisons 5

The same pattern runs BFS and DFS under adjacency-list and adjacency-matrix resource models: identical program, identical traversal, representation-sensitive costs (32 vs 44 for the worked BFS example).

What is proved and what is not, yet

All libraries build with no sorry and depend only on the three standard axioms (propext, Classical.choice, Quot.sound). The examples are executed and checked at build time.

Libraries

ResourceAware

The framework: free programs, semantics and cost-model records, the generic interpreter, ordered traces, erasure and reweighting, and the graph interface with resource models.

TextbookAlgorithms

Case studies from Kleinberg–Tardos: BFS and DFS (Chapter 3), MergeSort (Chapter 5) — correctness and complexity, per algorithm.

Examples

Executable demonstrations. Every number above comes from a #eval or #guard you can run yourself.

ThirdParty

Relationship to CSLib and AlgoLean

ResourceAware is an independent package built on CSLib (pinned dependency; the free-monad and TimeM foundations are CSLib's, used with gratitude). AlgoLean is the closest related project — a free-monad algorithms-and-complexity library on the same CSLib foundations. The designs are complementary: AlgoLean spans many computational models with a single model record per query type; ResourceAware separates semantics from cost as independent structures, keeps ordered traces, and focuses on deep textbook case studies. Selected reusable components here are candidates for focused upstream CSLib contributions.
